# 登录与接口反滥用设计

## 1. 安全边界

浏览器发出的任何字段都可以被 BP、脚本或无头浏览器修改，包括邮箱、设备信息、指纹、User-Agent、验证码请求参数和 Origin。因此：

- `X-Device-Info`、Canvas/WebGL 指纹只作为弱信号，不能作为认证凭据。
- 不能在前端放“签名密钥”；前端代码和请求签名都可以被重放或改写。
- 认证依据是 HTTPS 传输、服务端生成的验证码、JWT/会话、服务端风控状态和一次性挑战。
- 生产环境必须使用 HTTPS、可信反向代理、严格 CORS、CSRF 防护和安全响应头。

## 2. 请求链路

所有请求按以下顺序处理：

1. 反向代理清洗并覆盖 `X-Forwarded-For`，应用默认只使用 `remoteAddr`。
2. 网关限制请求体、Header 长度、连接数、请求速率和并发；超限返回 `429`，不执行数据库和邮件操作。
3. 解析客户端会话，校验 JWT 签名、过期时间、会话是否 active、账号状态是否可用。
4. 对登录和验证码接口执行风险评估；需要挑战时返回 `403` + `challengeId`，不发送验证码。
5. 业务处理成功后写入审计事件，事件只记录哈希化 IP、设备 ID 和必要上下文，不记录验证码明文或完整 JWT。

## 3. 验证码发送策略

服务端按多个维度分别限流，不能只按 IP：

| 维度 | 建议限制 | 触发后果 |
| --- | --- | --- |
| 邮箱 | 1 次/60 秒，5 次/小时，20 次/天 | 邮箱冷却 |
| IP | 5 次/10 分钟，30 次/小时 | IP 冷却/挑战 |
| IP + 邮箱 | 1 次/60 秒，10 次/小时 | 组合冷却 |
| 设备会话 | 3 次/10 分钟 | 挑战 |
| 全局 | 受邮件供应商配额约束 | 熔断并告警 |

验证码必须是 CSPRNG 生成、服务端保存哈希、5 分钟过期、最多错误 5 次，成功或超过错误次数立即作废。发送接口使用服务端生成的一次性 `idempotencyKey`，相同请求只返回原结果，不能重复发信。

验证码发送前的风险等级：

- `LOW`：正常发送。
- `MEDIUM`：完成 Turnstile/hCaptcha 等服务端可验证挑战后发送。
- `HIGH`：拒绝发送并记录原因；短时间内连续高风险时冻结邮箱/IP。

响应只返回通用文案和剩余秒数，不透露“邮箱是否注册”。

## 4. 登录风控评分

评分必须由服务端计算，建议初始规则：

- 新设备：+20
- 新国家/地区或短时间地理跳变：+25
- IP/ASN 属于公开代理、数据中心或 Tor：+30
- 同一 IP 多邮箱：+20
- 同一设备短时间多账号：+20
- 验证码错误：每次 +15
- 请求频率、路径序列、并发异常：+20 至 +50
- 指纹与 UA/屏幕/平台明显矛盾：+20
- 已验证设备、稳定会话、正常行为：-10 至 -30

处置阈值：

- `0-39`：放行。
- `40-69`：要求人机挑战，挑战通过后放行并降低分数。
- `70-99`：暂时阻断登录/验证码 10 分钟，撤销新建会话。
- `100+`：账号进入 `LOCKED_REVIEW`，撤销全部会话并要求解锁流程。

单条规则不能直接永久封号。永久封禁必须有多信号证据、审计记录和管理员复核。

## 5. 账号状态与解锁

建议给 `t_user` 增加：

```text
security_status: NORMAL | CHALLENGE | LOCKED_TEMP | LOCKED_REVIEW | BANNED
security_until: datetime
security_reason_code: varchar(64)
security_version: bigint
```

解锁流程：

1. `LOCKED_TEMP` 到期自动恢复，但仍需一次人机挑战。
2. `LOCKED_REVIEW` 只能通过已验证邮箱 + 人机挑战 + 冷却期申请解锁。
3. `BANNED` 不允许自助解锁，由管理员审核；管理员操作必须记录操作者、原因和工单号。
4. 解锁后撤销旧 JWT、重置验证码错误计数、保留风险事件，避免立即重新攻击。

## 6. 反爬与无头浏览器

不要用单一“是否无头”字段封禁。采用组合信号：请求速率、并发、页面访问序列、资源命中率、Cookie/JS 挑战完成率、TLS/HTTP 特征、数据中心 ASN、账号行为和设备稳定性。公开内容可以匿名访问，但必须分页上限、游标、防重复抓取和缓存；敏感写接口必须登录并带幂等键。

对无头浏览器只提高风险分，不做绝对阻断。合法自动化客户端应使用独立 API key、配额和明确 User-Agent，而不是伪装浏览器。

## 7. 请求劫持与参数篡改

HTTPS 可以防止链路上的第三方窃听和篡改，但无法阻止用户在自己浏览器中用 BP 修改请求。服务端必须：

- 每个参数重新做类型、长度、格式、枚举、权限和业务状态校验。
- 邮箱验证码只能绑定服务端生成的 challenge、邮箱哈希、用途和过期时间。
- 所有写操作使用服务端主体身份，不信任 body 中的 `userId`、role、price、ownerId。
- 敏感操作增加短时二次确认、幂等键和重放保护。
- CORS 使用明确 allowlist，不使用 `*` 搭配凭证；Cookie 会话使用 `HttpOnly; Secure; SameSite`。
- JWT 只放短期 access token，配合可撤销 refresh/session；日志不得打印 token。

## 8. 审计、监控和告警

记录 `eventId、时间、用户哈希、IP 哈希、ASN、设备哈希、UA 摘要、接口、结果、风险分、规则命中、challengeId、traceId`。验证码明文、Authorization 原值、完整邮箱不写日志。监控验证码成功率、429 比例、挑战通过率、单 IP 多账号数、登录失败率、邮件供应商错误率和封禁误报率。

## 9. 当前代码对应的落地点

- `LoginDeviceService` 默认不再信任伪造的转发头；只有设置 `SECURITY_TRUST_FORWARDED_HEADERS=true` 才读取代理头。
- `EmailController` 已按 IP + 邮箱限流；仍需按上表补充小时/天级配额和 challenge 校验。
- 前端设备信息只能作为登录设备展示和弱风控信号，不能用于“安全绑定”。
- 生产部署时必须重启 Spring Boot，使配置和 class 生效；Redis 旧限流 key 需要自然过期或按精确 key 清理，不能执行 `FLUSHALL`。

## 10. 验收标准

- 修改任意前端设备字段不能绕过服务端 challenge、权限和限流。
- 伪造 `X-Forwarded-For` 不能改变直接部署实例看到的 IP。
- 同一邮箱/IP/设备达到阈值后，邮件不会被调用，返回稳定的 `429/403`。
- 重放同一验证码、idempotency key、challenge 或敏感请求不会产生第二次副作用。
- 账号锁定会撤销现有会话，解锁后必须重新建立会话。
- 所有风控处置可由 traceId 追溯，且日志不包含验证码和 JWT 明文。
